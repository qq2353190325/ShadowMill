# 账号体系接入方案（客户端 × 后端）

> 状态：**已实现 v1.1**（2026-11-16 落地：后端 11 个用例全绿、客户端三工程 typecheck 全绿、真实接口联调 9/9 通过）
> 未纳入本轮：登录限流、验证码 `used` 语义拆分、Flyway 迁移、设置页 baseUrl 输入框（见 §8）
> 范围：把 ShadowMill 渲染层的「本地占位登录」换成 `demo` 后端的真实账号；后端同步把会话方案从 JWT 换成不透明会话 token。
> 前置决策（已定）：**可选登录** —— 未登录时本机全部创作功能照常可用，登录只承载云端能力（AI 额度 / 项目同步，后续版本落地）。
> 位置（用户视角）：「侧栏左下角 · 用户区」→「登录 / 注册」弹窗；注册流程多一步「邮箱验证码」。

---

## 1. 前提与三条不变量

1. **未登录 100% 可用**：账号不 gate 任何本机流水线（内容脚本 / 配音 / 字幕 / HTML 生成 / 成片）。
2. **登录态失效 ≠ 应用不可用**：token 过期或被撤只影响云端能力；界面切回「未登录」，不弹死循环、不阻断当前操作。
3. **token 不出主进程**：渲染层只拿展示字段（邮箱 / 昵称 / 过期时间），token 只存在于主进程内存 + `safeStorage` 加密文件。

## 2. 令牌策略（本方案的核心决策）

### 2.1 结论

**持久化登录不靠 JWT，靠可吊销的服务端会话。**

| 方案 | 持久化 | 可吊销 | 改动量 | 结论 |
|---|---|---|---|---|
| **A. 不透明会话 token** | ✅ 30 天滑动 | ✅ 即时 | 后端 ~半天，**净减代码** | **选它** |
| B. JWT + refresh token | ✅ | ✅（refresh 层） | ~2 倍（轮换 / 复用检测 / 单飞刷新） | 将来接 Web 端再考虑 |
| C. 只把 JWT TTL 拉到 30 天 | ✅ | ❌ | 改一行配置 | 仅限「随时可全量重置」阶段，不选 |

### 2.2 为什么不选 JWT（三条，都对得上现有代码）

1. **不可吊销**：JWT 自包含，签发后到期前作废不了（现实现无 jti、无黑名单）。改密码 / 封号 / 设备丢失都踢不下线；而"持久化"意味着这张票据要在用户机器上躺几十天。
2. **持久化 = 拉长 TTL = 扩大泄露窗口**：从 2 小时变成 30 天，且桌面端票据一定落盘。
3. **这个项目拿不到 JWT 的唯一好处**：`AuthService.currentUser` 解析完 payload 仍然 `findById` 查了一次库。既然每请求都查库，"无状态"收益为零，剩下的全是成本——包括 `JwtTokenService` 手拼 JSON、正则取 claim、不校验 `alg` 的脆弱实现（P1）。

> 换成 A 之后，`JwtTokenService`（**152 行**）整份删除，`JwtProperties`（34 行）与 `app.jwt.*` 配置删除，`spring-boot-starter-security-crypto` 只留 BCrypt。
> 注意：**代码量只是基本持平**（删 186 行、加约 180 行），省掉的不是行数，而是「手拼 JSON / 正则取 claim / 不校验 alg / 依赖客户端时钟」这一整类最容易出错的逻辑。

### 2.3 令牌规格

- 生成：`SecureRandom` 32 字节 → Base64URL（无填充，43 字符），前缀 `sm_`（便于日志脱敏与泄露扫描）。
- 存储：**只存 `sha256(token)` 的 hex（64 字符）**，不存明文；查库按 unique 索引命中，无需常量时间比较。
- 有效期：30 天，**滑动续期**（见 3.3 的 touch 规则）。
- 吊销：`revoked_at` 置位；改密码 / 封号时批量置位该用户全部会话。
- 日志：任何位置都不得打印完整 token（只打前 8 位 + 长度）。

## 3. 后端改动（`demo/`）

### 3.1 表结构（追加到 `src/main/resources/db/schema.sql`）

```sql
-- ---------------------------------------------------------------------
-- auth_sessions：登录会话（不透明 token，服务端可吊销）
--   查询模式：token_hash 唯一索引命中；user_id 用于「全部下线」与清理
-- ---------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS auth_sessions
(
    id           BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id      BIGINT      NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    token_hash   CHAR(64)    NOT NULL,
    device_name  VARCHAR(64),
    created_at   TIMESTAMP   NOT NULL,
    last_seen_at TIMESTAMP   NOT NULL,
    expires_at   TIMESTAMP   NOT NULL,
    revoked_at   TIMESTAMP,
    CONSTRAINT uk_auth_sessions_token_hash UNIQUE (token_hash)
);

CREATE INDEX IF NOT EXISTS idx_auth_sessions_user ON auth_sessions (user_id);
```

> `device_name` 当前由客户端传 `windows / macos`（可选），为将来「设备管理」留位；本期不展示、不校验。
> 时间列沿用现有 `TIMESTAMP + LocalDateTime` 口径，与 `users` 保持一致（改成 `TIMESTAMPTZ + Instant` 是另一笔 P2 债务，本方案不混做）。

### 3.2 接口

| 方法 | 路径 | 变化 | 说明 |
|---|---|---|---|
| POST | `/api/auth/send-code` | 不变 | — |
| POST | `/api/auth/register` | 不变（201） | 内部改为签发会话 |
| POST | `/api/auth/login` | 不变 | 内部改为签发会话 |
| GET | `/api/auth/me` | 不变 | 内部改为查会话 + 滑动续期 |
| POST | `/api/auth/logout` | **新增** | 带 `Authorization: Bearer`，撤销当前会话；幂等返回 200 |
| POST | `/api/auth/logout-all` | 可选（P2） | 撤销该用户全部会话 |

**`AuthResponse` 字段名与形状完全不变**（`token / tokenType / expiresInSeconds / user`），所以客户端契约零改动：

- `tokenType` 仍为 `"Bearer"`；
- `expiresInSeconds` = 当前会话剩余秒数（首次约 `2592000`）。

### 3.3 会话生命周期

| 时机 | 行为 |
|---|---|
| 登录 / 注册成功 | 插入一行：`expires_at = now + 30d` |
| 每次带 Bearer 的请求 | 按 `sha256(token)` 查行 → 校验 `revoked_at == null` 且 `expires_at > now` → 命中则**距上次 touch ≥ 1 小时**时更新 `last_seen_at = now` 且 `expires_at = now + 30d`（一条 UPDATE） |
| `logout` | 该行 `revoked_at = now` |
| 改密码 / 封号 | 该用户全部行置 `revoked_at` |
| 清理 | 过期且已撤销的行可异步删（本期不做定时任务，登录时顺手删本人过期行即可） |

> 「1 小时一次 touch」是为了避免每次请求都写库（写放大）。代价：连续 30 天不打开应用则需重登——可接受。

### 3.5 响应体加业务码（否则客户端只能猜）

现状 `ApiResponse` 只有 `success / message / data`，客户端无法区分「验证码错误 / 已过期 / 次数超限」——都落成 HTTP 400 + 一句话。

```java
public record ApiResponse<T>(boolean success, String code, String message, T data) {
    public static <T> ApiResponse<T> ok(String message, T data) { return new ApiResponse<>(true, "OK", message, data); }
    public static <T> ApiResponse<T> fail(String code, String message) { return new ApiResponse<>(false, code, message, null); }
}
```

`BizException` 带 `code`（与 HTTP 状态并存），`GlobalExceptionHandler` 原样透出。业务码表（客户端 §4.5 按它映射）：

| code | HTTP | 场景 |
|---|---|---|
| `EMAIL_TAKEN` | 409 | 邮箱已注册 |
| `CODE_INVALID` | 400 | 验证码错误 |
| `CODE_EXPIRED` | 400 | 验证码过期 |
| `CODE_TOO_MANY` | 400 | 错误次数超限、已作废 |
| `CODE_COOLDOWN` | 429 | 重发冷却中 |
| `UNAUTHORIZED` | 401 | 邮箱或密码错误 / token 无效或过期 |
| `BAD_REQUEST` | 400 | 参数校验失败 |

### 3.6 安全项（与本次一起做，否则"能上线"是假的）

1. **dev-mode fail-fast**：非 `dev` profile 下 `app.mail.dev-mode=true` 直接启动失败（`@Profile` 外的 `ApplicationRunner` 或 `@PostConstruct` 校验）。现在默认是 `true`，一行忘改就是「任意邮箱无需验证码即可注册」。
2. **登录限流**：同一邮箱 + IP 的失败次数（本轮至少做内存计数：5 次 / 15 分钟）。
3. **验证码存哈希**：`verification_codes.code` 改成 `sha256(code)`（P1，可与本次同批）。

### 4.4 数据流

**启动**：主进程读 `account.bin` 只判断"有没有"，不阻塞建窗 → 渲染层挂载后异步 `account:me` → 200 写展示态 / 401 清 token 静默切未登录 / **NETWORK 保留上次展示态**（这是"离线可用"的落点：断网不掉登录态）。

**注册**：点「发送验证码」→ 倒计时用**后端返回的 `resendAfterSeconds`**（不写死 60s，否则两端冷却策略一改就漂移）→ 填码提交 → `account:register` → 主进程存 token、回 `AccountSession` → `signIn()`。

**401 统一出口**：`api.ts` 一处判定 → 清 token + `UNAUTHORIZED` → 渲染层切未登录 + toast「登录已过期，请重新登录」。不要每个调用点各写一遍。

**dev 调试码**：只有 `!app.isPackaged` 时主进程才把 `debugCode` 透给渲染层；渲染层不做环境判断。

### 4.5 错误码映射

`account:send-code` / `register` / `login` 的 HTTP 响应 → 枚举（`api.ts` 内一张表，**不复用 `shared/errors.ts`**：那里 401 的文案是「API Key 无效」，会把账号过期说成 Key 问题）。

| 后端 | code | 用户看到 |
|---|---|---|
| 409 + `EMAIL_TAKEN` | `EMAIL_TAKEN` | 该邮箱已注册，请直接登录 |
| 400 + `CODE_INVALID` | `CODE_INVALID` | 验证码不正确 |
| 400 + `CODE_EXPIRED` | `CODE_EXPIRED` | 验证码已过期，请重新获取 |
| 400 + `CODE_TOO_MANY` | `CODE_TOO_MANY` | 验证码错误次数过多，请重新获取 |
| 429 + `CODE_COOLDOWN` | `CODE_COOLDOWN` | 发送太频繁，请稍后再试 |
| 401 | `WRONG_PASSWORD` | 邮箱或密码错误 |
| 401（`/me`） | `UNAUTHORIZED` | 登录已过期，请重新登录 |
| 连不上 / 超时 | `NETWORK` | 无法连接账号服务器，请检查网络 |
| 5xx | `SERVER` | 账号服务暂时不可用，请稍后重试 |
| safeStorage / 写盘失败 | `STORAGE_FAILED` | 无法保存登录状态，请检查磁盘权限 |

**后端无 `code` 字段时的降级**：按 HTTP 状态映射（409 / 429 / 401 / 400→`BAD_REQUEST` 统一文案），体验变差但可用。这也是 §3.5 值得做的那 25 行的原因。

## 6. 风险与已知取舍

| 项 | 取舍 |
|---|---|
| 每请求一次会话查询 | 单条 unique 索引查询，本量级可忽略；换来即时吊销 |
| 滑动续期写放大 | 1 小时一次 touch；连续 30 天不打开应用需重登 |
| `safeStorage` 不可用（部分 Linux） | 退化为内存态，重启需重登——比明文落盘正确 |
| 注册必须联网 + 验证码 | 离线用户无法注册，UI 文案要明说 |
| token 未做 refresh | 不需要：滑动 30 天已满足桌面端"记住我" |
| `TIMESTAMP` 无时区 | 沿用现状；`Instant + TIMESTAMPTZ` 是另一笔 P2 |
| 设备管理 / 会话列表 | 本期只落库不展示 |

## 附：若坚持 JWT（方案 B 的最小形态）

只在将来要接 Web / 第三方、或无状态成为硬需求时才走这条：

- 表 `refresh_tokens(id, user_id, token_hash CHAR(64), family_id UUID, expires_at, revoked_at, created_at, last_used_at)`；
- `POST /api/auth/refresh` 旋转刷新令牌，旧令牌立即作废；**检测到已作废令牌被复用 → 整族吊销**（防窃取重放）；
- access JWT 15–60 分钟，客户端 `api.ts` 做**单飞刷新**（并发请求只触发一次 refresh）；
- 工作量约为方案 A 的两倍，且 `JwtTokenService` 必须同时修 `alg` 校验与 JSON 解析（换成 Nimbus/JJWT，不再手写）。
