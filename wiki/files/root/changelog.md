# CHANGELOG.md

> 影坊 / ShadowMill 的**唯一**变更记录：一个版本一个区块，每次修改一条，版本号与 `package.json` 的 `version` 严格一致

- **位置**：工程根
- **类型**：变更记录（更新日志 = 修改日志 = 版本记录，三者是同一份文件）
- **版本号归属**：`package.json` 的 `version`（当前 `0.0.3`，该区块现为「待发布」）

## 1. 定位

- 本文件是**本工程唯一的变更记录**：任何改动都要落在它里面，**不要另建第二份**（`README.md` 的「当前进度」只是给使用者的概览，不是变更记录）。
- 一个版本一个区块，每个条目 = **一次修改**：发布时只看本文件就能知道这一版改了什么。
- 写入规则（先看后写 / 改完必记 / 改两次算完整版 / 版本号只有一处 / 粒度）的正文在根目录 [`agents.md`](../../../agents.md) 第三节「更新日志（CHANGELOG.md）」与第五节关键约定的第 3、4 条。

## 2. 结构

区块顺序**越上面的版本越新**：

```
## 未发布（下一版本）        ← 永远在最顶；不打算进当前版本的改动先记这里
## [0.0.3] - …（待发布）     ← 最新版本，仍在施工，条目会继续追加
## [0.0.2] - …
## [0.0.1] - …
```

- **`## 未发布（下一版本）` 永远在最顶**：新改动如果没打算进当前版本，就先记在这里；发版时整块并到当次版本号下。
- 其下是**最新版本区块**，再往下是**更早版本**（版本倒序）。
- 每个版本区块可带一行 `>` 引用块说明本版主题。

## 3. 条目与表格

- 表格列（`0.0.3` / `0.0.2` / `未发布` 区块为 **5 列**，`0.0.1` 区块**少一列、只有前 3 列**）：

  ```
  | # | 日期 | 修改 | 影响范围 | 验证 |
  ```

  | 列 | 写什么 |
  | --- | --- |
  | `#` | 条目编号 |
  | `日期` | 这次修改的日期 |
  | `修改` | `[标签]` + 改动内容 |
  | `影响范围` | 文件 / 页面 / 模块 |
  | `验证` | 实际跑过什么（如 `npm run typecheck` 全绿、`npm run dev` 手测通过、未验证） |

- **编号**：条目编号 = 该版本内**第几次修改**（`#1`、`#2`…），越靠后越新。
- **插入位置**：**新条目插在该区块表格的最上方**——最新改动一眼可见，读到底部就是这一版最早做的事。
- **每条必带**：`[标签]` 类别 · 影响范围 · 验证方式。

## 4. 标签与完整版判定

- 标签只有七个，只能从中选；跨类别的改动拆成多条：

  | 标签 | 用在什么改动上 |
  | --- | --- |
  | `[新增]` | 新功能 / 新文件 |
  | `[修改]` | 行为变化 |
  | `[修复]` | 缺陷修复 |
  | `[重构]` | 结构调整 |
  | `[优化]` | 性能 / 体验 |
  | `[文档]` | 文档改动 |
  | `[工程]` | 构建、依赖、打包、脚本 |

- **`[完整版]` / `[待续]` 判定**：同一个功能在**当前版本**里改到 **2 条及以上** → 在它**表格最上方的那一条**（最新一次修改）标 `[完整版]`，并注明累计次数（如 `×2`）；只改过 **1 条**、还在演进中的标 `[待续]`。
- 每个版本区块**末尾有一行「本版『完整版』判定」汇总**，把本版哪些功能已到完整版列出来，发布时一眼可见。

## 5. 版本号与发版流程

- **版本号只有一处**：`package.json` 的 `version`。本文件按它记录，**不自己发明版本号、不在别处另写版本表**。
- 发版步骤：

  1. `npm version patch --no-git-tag-version` 升 `package.json` 的 `version`（不建 git tag）；
  2. 把该版本区块标题里的「**待发布**」换成实际发布日期；
  3. 在最上面新开一个空的 `## 未发布（下一版本）` 区块。

## 7. 维护约定

- **不许另建第二份日志**：更新日志 / 修改日志 / 版本记录都是本文件，别再开 `CHANGELOG-*.md` 之类的副本。
- **漏记视同改动未完成**：每次修改都要在当前版本区块记一条；**同一功能的后续改动更新已有那条**（并把它移到该区块表格最上方），不要同一件事反复新起行。
- **先看后写**：动任何代码前先看本文件最上面的当前版本区块（这一版已经改了什么），据此决定「追加一条，还是更新已有条目」，避免重复实现、避免与已写下的决定打架。
- **文档之外的动作**：日志之外还要按约定同步 wiki（规则见根 [`agents.md`](../../../agents.md) 第五节关键约定 5、6）。

## 8. 与其他文件的关系

| 关联文件 | 关系 |
| --- | --- |
| `package.json` | 区块标题里的版本号与它的 `version` 字段一致；发版只改这一处；`npm version patch --no-git-tag-version` 升的也是它 |
| [`agents.md`](../../../agents.md) | 第三节「更新日志（CHANGELOG.md）」是本文件写入规则的正文；第五节关键约定 3、4 把「改前先看、改完必记」定为硬约定 |
| `README.md` | 面向使用者的说明文档（功能 / 实现 / 流程 / 进度），开头引用区与「六、当前进度 → 已完成」指向本文件；内容不重复转述 |
| `REFACTOR_PLAN.md` | 重构计划与实施记录，属项目级说明文档；不等同于变更记录 |
| `wiki/` 各文档 | 源码级知识库；代码改动落地后，本文件记「改了什么」，wiki 记「现在是什么样」，两者都要更新 |
